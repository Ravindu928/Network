Chapter 3 · Scene 1 · The transport layer

A letter for the right person

Alice lives in a busy house. So does Bob. Inside Alice's house, her web browser, her music app and her chat app all want to send letters. Inside Bob's house, a web server and a DNS server wait for mail.

Between the two houses runs the postal service, the network layer. It's very good at getting an envelope from one house to another. But it has no idea who lives inside.

So the network layer gives house-to-house delivery, and the transport layer turns that into person-to-person delivery. Transport protocols only run inside the houses, the end systems. Routers on the way never look inside the inner envelope.

Scene 2 · Multiplexing and demultiplexing

The sorting puzzle

Bob's mailroom is busy. Letters pour in from all over town, and it must drop each one into the right mailbox. Packing many programs' letters into one stream of envelopes is multiplexing (at the sender). Sorting them back out is demultiplexing (at the receiver).

Every envelope carries four things the mailroom can read: the source IP and destination IP (the house addresses), and the source port and destination port (the door numbers).

A TCP socket is identified by the full 4-tuple: source IP, source port, destination IP, destination port. That's why a web server on port 80 can keep a separate mailbox for every single visitor.

Scene 3 · Connectionless transport: UDP

The postcard

Alice's computer needs to ask a DNS server one tiny question: "What's the address of example.com?" Setting up a whole tracked delivery for that feels silly.

Sounds bad? UDP has real plusses: no setup round trip, a tiny 8-byte header, no connection state to keep, and no congestion control slowing it down. That's why DNS, SNMP, streaming media and HTTP/3 use it. If an app needs reliability over UDP, the app adds it itself.

Scene 10 · TCP congestion control

Feeling for the speed limit

Alice keeps a number called the congestion window, cwnd: how many letters she may have on the road at once. Her rate is roughly cwnd / RTT.

Doubling each RTT is slow start. Above the threshold ssthresh, she adds just 1 letter per RTT: additive increase. On loss she cuts back: multiplicative decrease. Together, AIMD makes a sawtooth.

Fairness can be dodged: UDP apps don't throttle at all, and a browser can open many parallel TCP connections.

Newer tricks

CUBIC
Remembers Wmax, where loss happened, climbs back fast at first and carefully near it. Default in Linux and most web servers.
Delay-based
Keep the pipe "just full enough, but no fuller": compare measured throughput with cwnd / RTTmin. Google's BBR works this way.
ECN
A congested router marks two bits in the IP header; Bob echoes it (ECE bit) so Alice slows down without any loss.

Loss-based TCP pushes until the bottleneck link drops a letter. Pushing harder there only grows the queue and the delay.

Scene 11 · Evolution of the transport layer

A faster courier on top of UDP

TCP and UDP have carried the Internet's mail for 40 years. Lately, some transport jobs have moved up into the application, riding on UDP. The star is QUIC, which powers HTTP/3 in Chrome, YouTube and Google's servers.
